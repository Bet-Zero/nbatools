## Alternatives considered

### A. Keep repairing sample strings one at a time - not selected

Useful intake, insufficient engineering strategy. Samples underrepresent
combinations, misidentify data gaps as parser issues and encourage special-case
patches. They remain regression/acceptance evidence inside dependency-led work.

### B. Finish a universal engine rewrite before features - not selected

The existing service, metric helpers, result types and renderers are usable
integration points. A replacement would create a long period with two engines
or lost behavior without a demonstrated need. Instead, consolidate shared sample
and operation semantics while shipping specific real consumers. Reconsider only
when a measured limit survives smaller repairs.

### C. Put an LLM in front immediately - not selected as a prerequisite

A constrained language interpreter may improve wording coverage, but it cannot
supply missing NBA data or make an unimplemented operation execute. It adds
runtime cost/access/latency and semantic verification needs. The present cost
policy also prevents assuming a new metered service is authorized.

Structured output constrains form, not the truth of values or interpretation:
[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
and [the original limitations explanation](https://openai.com/index/introducing-structured-outputs-in-the-api/).
The [PICARD paper](https://arxiv.org/abs/2109.05093) is evidence that constrained
formal-query decoding is a real option, not evidence it outperforms this app or
solves its current engine gaps. No model/provider benchmark was run here.

After execution parity, use measured language-only failures to decide on one
bounded held-out comparison. A winning interpreter would target the same
validated engine, never invent numerical answers or generate unrestricted code.
This is a conditional engineering decision, not an owner requirement to choose
models and not a ban on replacing a parser that proves inadequate.

### D. Expand QA/governance before delivery - not selected

The required testing layers mostly exist. The need is better assertions at the
correct layer, numerically grounded expectations and remote access to relevant
data, not a new test brand or another manual review funnel. Preserve valuable
failure-sensitive checks; do not turn every theoretical improvement into a blocker.

### E. Dependency-led capability delivery plus parallel data/operation - selected

Identity and sample correctness unlock trustworthy calculations; consistent
operations unlock multiple families; composition prevents repeating work per
route. Source reconnaissance runs early because missing coverage can dominate
elapsed time. Deployment and refresh run alongside features because a correct
local answer is not the delivered product. This is the engineering rationale
for the active A/B/C/D/O/E plan, independent of the owner's example workflow.

## Review risks retained explicitly

- Actual source availability and full season/key coverage need execution access.
- Deployed cold/warm latency and cost-control enforcement have not been freshly
  measured here. Proposed response-time targets in the plan are recommendations.
- Some apparent phrase/filter gaps may already work under another path. Reproduce
  before changing code; do not overwrite valid behavior based on old examples.
- Full historical careers and specialized metrics may need independent sources;
  a partial range cannot silently satisfy an all-time claim.
- Independent reviewers must have the relevant data. Multiple agents inspecting
  the same output are not a substitute for independently established expectations.
- Later requirements may change priorities; the lead must record the evidence,
  not require routine owner phase-selection or restart a general audit.
